# Макро-шеф

Агент для хакатону «Сільпо AI Factory», який читає історію покупок гостя, рахує реальний
дефіцит білка й цукру, і збирає тижневий кошик, що цей дефіцит закриває — не дорожчий за
звичний.

## Проблема

Гість не логує їжу вручну. Замість цього агент:

1. читає історію покупок через MCP `https://mcp.silpo.ua/mcp`;
2. рахує реальний БЖВ-профіль і дефіцит по білку й цукру;
3. збирає тижневий кошик, що закриває дефіцит, з урахуванням акцій;
4. **переоптимізовує кошик**, якщо товару немає в наявності — перераховує все з нуля, а не
   підставляє заміну 1-в-1;
5. застосовує сертифікати, промокоди, балабонуси;
6. доводить до валідованого checkout.

Здоровіший кошик не дорожчий за звичний.

## Архітектура

```
Telegram Mini App ──► Backend (.NET 8) ──► MCP Silpo (HTTP, OAuth 2.1 + PKCE)
                            ├──► Postgres          (токени, кеш, McpCalls)
                            ├──► MakroChef.Solver   (Google.OrTools, CP-SAT)
                            └──► Anthropic API      (назви, пояснення — не підбір товарів)
```

Ключове архітектурне рішення: **LLM не підбирає товари.** Товари підбирає MILP/CP-SAT солвер —
детермінований і відтворюваний. LLM тільки нормалізує назви з чека й пояснює свопи. MCP-клієнт —
чистий I/O, жодної бізнес-логіки.

Усе на C#/.NET 8, включно з солвером (Google.OrTools, у процесі, без окремого сервісу чи
контейнера).

### Проєкти рішення

| Проєкт | Відповідальність |
|---|---|
| `MakroChef.Domain` | Доменні моделі: солвер, кошик, профіль, OAuth, каталог — без залежностей |
| `MakroChef.Mcp` | Клієнт MCP (офіційний SDK `ModelContextProtocol`), OAuth 2.1+PKCE, кеш, backoff |
| `MakroChef.Nutrition` | `INutritionResolver` — точний БЖВ з MCP або категорійний індекс + Open Food Facts |
| `MakroChef.Solver` | CP-SAT модель кошика (`BasketSolver`) |
| `MakroChef.Agent` | Оркестрація: профайлер, підбір кандидатів, збірка кошика, переоптимізація, checkout |
| `MakroChef.Data` | EF Core + Postgres |
| `MakroChef.Api` | ASP.NET Core API, CLI-команди (`auth`, `probe`), трейс-панель, статика Mini App |
| `MakroChef.Tests` | xUnit, 66+ тестів, stub MCP-сервер на офіційному SDK (не HTTP-мок) |

## Запуск

Потрібно: .NET 8 SDK, Docker.

```bash
git clone <repo>
cd MakroChef
docker compose up -d          # Postgres
dotnet build
dotnet test                   # 66+ тестів, усі проходять без мережі й без акаунта
dotnet run --project src/MakroChef.Api
```

API підніметься на `http://localhost:5077`. Trace-панель: `/web/trace/index.html?sessionId=<guid>`.
Telegram Mini App (на моках): `/web/app/index.html`.

### Автентифікація в Сільпо

```bash
dotnet run --project src/MakroChef.Api -- auth
```

Виведе посилання на `/authorize` — відкрийте його і залогіньтесь (телефон + SMS). Dynamic
Client Registration відбувається автоматично, реального `client_id` заздалегідь не потрібно.

### Проба покриття нутрієнтів

```bash
dotnet run --project src/MakroChef.Api -- probe
```

Читає реальну історію покупок і генерує `docs/coverage-report.md` — від цього залежить, який
з двох `INutritionResolver` використовувати (див. «Чесні обмеження» нижче).

## Чесні обмеження

- **Живий прогін не перевірений.** Кожен виклик до реального MCP Сільпо потребує акаунта з
  телефоном і SMS-кодом (`BLOCKERS.md` B-2) — його немає в CI/розробницькому середовищі цієї
  сесії. Уся логіка написана і покрита тестами на детермінованих фікстурах / stub-сервері
  (реальний MCP SDK, не HTTP-мок), але точні поля відповідей `get_product_details`,
  `get_shopping_cart_by_id` тощо — здогад, зроблений через `tools/list` (там є лише вхідні
  схеми, не вихідні). Один реальний прогін `auth` дійшов до Dynamic Client Registration на
  `mcp.silpo.ua` і отримав справжній `client_id` — далі потрібен людський логін.
- **Поріг профайлера (4.0) не обраний.** `INutritionResolver` має дві готові реалізації (точний
  БЖВ vs категорійний індекс + Open Food Facts), перемикання — одним рядком конфігу після
  живого прогону `probe` і рішення розробника про поріг 60% покриття.
- **Палітра дизайну відхиляється від спеки в двох місцях.** `--text-compare` (обидві теми) і
  темний `--text-muted` з розділу 10.1 не проходять WCAG AA 4.5:1 — підібрані ближчі відтінки
  тієї ж гами. Деталі в `CHECKPOINTS.md`.
- **Пул кандидатів (200-400 товарів) не перевірений у реальному масштабі** — stub-сервер не
  може підробити цілий каталог супермаркету, логіка перевірена на фікстурі меншого розміру.
- **9.1 (замикання циклу тиждень-до-тижня) не реалізовано** — перше, що ріжеться за порядком
  деградації (TASKS.md 10.3), якщо бракує часу.
- **Нутрієнти на одиницю товару — оцінка.** Якщо `get_product_details` не поверне вагу пакування,
  використовується дефолт 100 г, задокументовано в коді.
