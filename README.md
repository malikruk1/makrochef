# Макро-шеф

Агент для хакатону «Сільпо AI Factory», який читає історію покупок гостя, рахує реальний
дефіцит білка й цукру, і збирає тижневий кошик, що цей дефіцит закриває — не дорожчий за
звичний.

## Проблема

Гість не логує їжу вручну. Замість цього агент:

1. читає історію покупок через MCP `https://mcp.silpo.ua/mcp`;
2. рахує реальний БЖВ-профіль і дефіцит по білку й цукру;
3. збирає тижневий кошик, що закриває дефіцит, з урахуванням акцій;
4. **переоптимізовує кошик**, якщо товару немає в наявності — перераховує все з нуля, а не
   підставляє заміну 1-в-1;
5. застосовує сертифікати, промокоди, балабонуси;
6. доводить до валідованого checkout.

Здоровіший кошик не дорожчий за звичний.

## Архітектура

```
Веб-застосунок (web/app) ──► Backend (.NET 8) ──► MCP Silpo (HTTP, OAuth 2.1 + PKCE)
                                  ├──► Postgres          (токени, кеш, McpCalls)
                                  ├──► MakroChef.Solver   (Google.OrTools, CP-SAT)
                                  └──► Anthropic API      (пояснення свопів — опційно, не підбір товарів)
```

> Telegram Mini App був архітектурним вибором на старті (TASKS.md 0.3), не вимогою MCP чи
> хакатону. 2026-09-14 від нього відмовились — застосунок працює як звичайна веб-сторінка,
> Telegram SDK ніколи не використовувався в коді.

Ключове архітектурне рішення: **LLM не підбирає товари.** Товари підбирає MILP/CP-SAT солвер —
детермінований і відтворюваний. LLM тільки нормалізує назви з чека й пояснює свопи. MCP-клієнт —
чистий I/O, жодної бізнес-логіки.

Усе на C#/.NET 8, включно з солвером (Google.OrTools, у процесі, без окремого сервісу чи
контейнера).

### Проєкти рішення

| Проєкт | Відповідальність |
|---|---|
| `MakroChef.Domain` | Доменні моделі: солвер, кошик, профіль, OAuth, каталог — без залежностей |
| `MakroChef.Mcp` | Клієнт MCP (офіційний SDK `ModelContextProtocol`), OAuth 2.1+PKCE, кеш, backoff |
| `MakroChef.Nutrition` | `INutritionResolver` — точний БЖВ з MCP або категорійний індекс + Open Food Facts |
| `MakroChef.Solver` | CP-SAT модель кошика (`BasketSolver`) |
| `MakroChef.Agent` | Оркестрація: профайлер, підбір кандидатів, збірка кошика, переоптимізація, checkout |
| `MakroChef.Data` | EF Core + Postgres |
| `MakroChef.Api` | ASP.NET Core API, CLI-команди (`auth`, `probe`, `diag`), статика веб-застосунку |
| `MakroChef.Tests` | xUnit, 91 тест, stub MCP-сервер на офіційному SDK (не HTTP-мок) |

## Запуск

Потрібно: .NET 8 SDK, Docker.

```bash
git clone <repo>
cd MakroChef
docker compose up -d          # Postgres
dotnet build -f net8.0
dotnet test -f net8.0         # 91 тест, усі проходять без мережі й без акаунта
dotnet run --project src/MakroChef.Api -f net8.0
```

API підніметься на `http://localhost:5077`. Застосунок (усі 7 екранів, включно з трейс-панеллю
екрана 7): `http://localhost:5077/web/app/index.html`.

Опційно — реальні (не шаблонні) пояснення свопів на екрані 3: додайте `ANTHROPIC_API_KEY` у `.env`
(див. `.env.example`). Без ключа фіча повністю робоча — пояснення рахуються з тих самих чисел
за детермінованим шаблоном.

### Автентифікація в Сільпо

```bash
dotnet run --project src/MakroChef.Api -f net8.0 -- auth
```

Виведе посилання на `/authorize` — відкрийте його і залогіньтесь (телефон + SMS). Dynamic
Client Registration відбувається автоматично, реального `client_id` заздалегідь не потрібно.

### Проба покриття нутрієнтів

```bash
dotnet run --project src/MakroChef.Api -f net8.0 -- probe
```

Читає реальну історію покупок і генерує `docs/coverage-report.md` — від цього залежить, який
з двох `INutritionResolver` використовувати (див. «Чесні обмеження» нижче).

## Чесні обмеження

- **Живий прогін підтверджений — 30+ реальних знахідок.** Весь пайплайн (auth → profile → basket
  → reoptimize → checkout → swaps → week-over-week → trace) прогнаний проти реального акаунта
  Сільпо. Кожен реально знайдений розбіжність між здогадом і фактичною MCP-схемою задокументований
  у `BLOCKERS.md` (30+ пронумерованих знахідок) — головний висновок сесії: **MCP-сервер тихо
  ігнорує невідомі імена параметрів і повертає `success:true`, нічого не змінивши**, тож кожен
  write-виклик (кошик, checkout, свопи) перевірявся дампом реальної JSON Schema через
  `dotnet run -- diag`, а не тільки читанням документації.
- **Профайлер (4.0) не потребує ручного вибору порогу.** `NutritionResolverFactory` автоматично
  обирає точний БЖВ-резолвер чи категорійний індекс+Open Food Facts на основі
  `CoverageProbe.CoveragePercent` (поріг 60%) на кожен запит — підтверджено проти реальних
  `product.attributes`.
- **Палітра дизайну відхиляється від спеки в двох місцях.** `--text-compare` (обидві теми) і
  темний `--text-muted` з розділу 10.1 не проходять WCAG AA 4.5:1 — підібрані ближчі відтінки
  тієї ж гами. Деталі в `CHECKPOINTS.md`.
- **Тиждень-до-тижня (9.1) — ретроспектива на історичних чеках.** Кожна позиція чека рахується як
  ~100 г (реальна вага з `get_product_details` для кожної позиції всієї історії — забагато
  MCP-викликів), явно позначено в UI як наближення.
- **Нутрієнти на одиницю товару — оцінка.** Якщо `get_product_details` не поверне вагу пакування,
  використовується дефолт 100 г, задокументовано в коді.
- **Дві з трьох задач LLM (TASKS.md 0.2) не реалізовані.** Пояснення свопів — готове
  (`ANTHROPIC_API_KEY`, опційне, з детермінованим фолбеком). Переклад вільного тексту на кшталт
  «без риби» у структуровані обмеження і нормалізація "брудних" назв з чека (реальні назви Сільпо
  вже чисті — актуальність цієї задачі під питанням) — не почато.
